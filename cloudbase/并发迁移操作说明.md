# CloudBase 并发迁移与线上写入操作说明

> `apply_game_action` 由 CloudBase 内部角色 `cloudbase_admin` 拥有，当前 SQL 编辑器的 `cloudbase_postgres` 无法覆盖它。不要对该旧函数执行 `ALTER FUNCTION` 或 `CREATE OR REPLACE FUNCTION`。
>
> 本项目使用版本化函数 `apply_game_action_v31` 规避所有权限制：当前 `cloudbase_postgres` 已验证拥有 `public` schema 的 CREATE 权限，因此可以在 SQL 编辑器或管理通道创建、复写这个新函数。不要粘贴管理员密钥、访问令牌或 API Key 到仓库或聊天中。

## 后续线上写入规范

| 场景 | 允许的写入方式 | 禁止或避免的方式 |
| --- | --- | --- |
| 正常游戏操作（建房、加入、确认词语、描述、投票、爆灯、退出） | 前端调用受控 RPC：`create_game`、`join_game`、`apply_game_action` | 前端直接更新 `public.games.state`、`version` 或 `updated_at` |
| 数据库函数、表结构、RLS、索引、授权变更 | 新对象优先使用版本化名称；先迁移计划和只读核验，再执行 | 覆盖 `cloudbase_admin` 拥有的旧函数、重跑已完成迁移、`ALTER OWNER` |
| 临时数据修复 | 先运行带精确条件的 `SELECT` 预览和影响范围核验；人工确认房间号与行数后，在管理通道执行受限 SQL | 无条件 `UPDATE` / `DELETE`、直接修改整张游戏表 |

### 数据库变更固定流程

1. 在仓库新增或更新带版本号的 SQL 和对应只读核验 SQL；不覆盖既有迁移历史。
2. 本地执行测试、构建，并提交 Git；记录将要执行的对象和预期效果。
3. 在 CloudBase AI 中先生成迁移计划，确认 SQL 不包含未授权的 `DROP`、无条件写入或权限扩大。
4. 经人工确认后执行迁移；若目标是内部角色拥有的旧函数，改为新建版本化函数，不能直接覆盖。
5. 返回并留存工具参数、RequestId、受影响对象和只读核验结果。
6. 发布前端后完成双浏览器联机验收；验收不通过先回滚前端，不直接覆盖线上房间状态。

### 可复用的 CloudBase AI 提示词

```text
这是线上数据库变更。请先仅生成迁移计划，不执行。
确认 SQL 仅影响指定对象、没有 DROP/无条件 UPDATE 后，
优先新建版本化对象；不要覆盖 cloudbase_admin 拥有的函数。
不要 ALTER OWNER；不要重跑已完成迁移。
执行后返回：实际工具参数、RequestId、受影响对象和只读核验结果。
```

## 发布顺序

### 离谱法堂 Draft 0.3 / V6

1. 确认 V5 和 `hotfix-v5-court-join.sql` 已执行并通过核验。
2. 执行 `concurrency-v6-court-dual-vote.sql`；它只新增案件参考答辩字段、V6 双项选票表、V6 幂等表和版本化函数，保留 V5 对象。
3. 执行 `verify-v6-court-dual-vote.sql`，确认每一行 `ok` 都为 `true`。
4. 再部署调用 V6 RPC 的前端；不要先部署前端，否则创建房间会提示 V6 RPC 不存在。
5. 使用两个独立浏览器会话验证两人建房、两项可投同一候选、卷宗参考投票时出现、结果双奖项与双榜单。

> V6 新建房间与 V5 房间互不升级。发布前应结束仍在进行的 V5 测试房间；需要回滚时只回滚前端到 V5 提交，V6 新对象可保留。

### 已部署 V5 的离谱法堂环境

如果加入房间返回 `missing FROM-clause entry for table "join_court_game_v5"（DATABASE_42P01）`：

1. 只执行 `hotfix-v5-court-join.sql`，不要重跑整套 V5。
2. 执行 `verify-v5-court-join-hotfix.sql`，确认每一行 `ok` 都为 `true`。
3. 该热修复只替换 `join_court_game_v5(text,text,text)` 的函数体，不修改表、房间数据、RLS 或授权。
4. 执行后不需要重新构建前端，直接用两个独立域名或浏览器会话复测创建与加入。

1. 在 CloudBase 测试环境执行 `schema.sql`（已有环境跳过）。
2. 执行 `concurrency-v2.sql`，但不要执行文件末尾注释的 `revoke update(...)`。
3. 不执行 `concurrency-v3-special-roles.sql` 或 `concurrency-v3-1-special-roles-hotfix.sql`：它们尝试覆盖内部角色拥有的旧函数，在当前 CloudBase PG 环境会失败。
4. 执行 `concurrency-v3-2-versioned-rpc.sql`，创建可由当前管理员维护的 `apply_game_action_v31`。
5. 执行 `verify-v3-2-versioned-rpc.sql` 和 `verify.sql`，确认每一行 `ok` 都为 `true`。
6. 使用当前功能分支前端完成双浏览器验收。
7. 数据库验收通过后再发布新前端。
8. 确认线上新前端稳定后，执行：

```sql
revoke update(state, version, updated_at) on public.games from anon, authenticated;
```

9. 再次执行 `verify.sql` 并进行一次建房、加入、确认、描述、投票和下一轮回归。

> 当前线上函数体仍为 V2，因此本项目应采用第 4 步的版本化 RPC 方案；不要重跑旧 V3。

## 双浏览器最小验收

- 两个独立匿名会话同时确认词语，两人的确认结果都保留。
- 两人同时提交描述，两条描述都保留。
- 两人同时投票，两票都保留；最后两票同时提交只结算一次。
- 同一按钮快速双击只生成一次提交。
- 首次平票只进入一次复投，旧票轮请求收到“状态已更新，请重试”。
- 两人同时爆灯只能一人成功。
- 描述公开后的 5 秒等待期内可以发起平民指认；指认后直接进入投票且清空旧票。
- 平民指认每局仅一次，进入下一轮后不能再次使用；“再来一局”后恢复一次机会。
- 等待房间修改三项人数配置后，其余玩法开关保持不变。
- 投票淘汰空白牌时按特殊阵营重新判胜；开启翻盘时，空白牌也进入私密猜词判定。
- 一个会话提交后断网并恢复，重新进入后能看到服务端已保存结果。

## 回滚

如果新前端发布后出现阻断问题：

1. 回滚前端到上一个稳定提交。
2. 若已经收紧权限，临时恢复旧前端写权限：

```sql
grant update(state, version, updated_at) on public.games to anon, authenticated;
```

3. `game_actions` 和 `apply_game_action` 可以保留，不影响旧前端读取房间。
