# CloudBase 并发迁移与线上写入操作说明

> 不要使用 CloudBase PostgreSQL SQL 编辑器执行函数、表结构、RLS 或权限变更。该编辑器使用的 `cloudbase_postgres` 不是内部函数所有者，无法可靠执行 `ALTER FUNCTION` 或 `CREATE OR REPLACE FUNCTION`。
>
> 数据库结构变更应通过 CloudBase AI 的 `managePgDatabase` 管理通道执行，优先使用迁移能力；如工具确认需要直接执行，则明确指定逻辑角色 `postgres`。不要粘贴管理员密钥、访问令牌或 API Key 到仓库或聊天中。

## 后续线上写入规范

| 场景 | 允许的写入方式 | 禁止或避免的方式 |
| --- | --- | --- |
| 正常游戏操作（建房、加入、确认词语、描述、投票、爆灯、退出） | 前端调用受控 RPC：`create_game`、`join_game`、`apply_game_action` | 前端直接更新 `public.games.state`、`version` 或 `updated_at` |
| 数据库函数、表结构、RLS、索引、授权变更 | CloudBase AI：先 `planMigration`，再 `applyMigration`；如需执行 DDL，角色使用 `postgres` | PostgreSQL SQL 编辑器、重跑已完成迁移、`ALTER OWNER` |
| 临时数据修复 | 先运行带精确条件的 `SELECT` 预览和影响范围核验；人工确认房间号与行数后，在管理通道执行受限 SQL | 无条件 `UPDATE` / `DELETE`、直接修改整张游戏表 |

### 数据库变更固定流程

1. 在仓库新增或更新带版本号的 SQL 和对应只读核验 SQL；不覆盖既有迁移历史。
2. 本地执行测试、构建，并提交 Git；记录将要执行的对象和预期效果。
3. 在 CloudBase AI 中先生成迁移计划，确认 SQL 不包含未授权的 `DROP`、无条件写入或权限扩大。
4. 经人工确认后，通过 `managePgDatabase` 执行；函数/DDL 使用 `postgres` 逻辑角色。
5. 返回并留存工具参数、RequestId、受影响对象和只读核验结果。
6. 发布前端后完成双浏览器联机验收；验收不通过先回滚前端，不直接覆盖线上房间状态。

### 可复用的 CloudBase AI 提示词

```text
这是线上数据库变更。请先仅生成迁移计划，不执行。
确认 SQL 仅影响指定对象、没有 DROP/无条件 UPDATE 后，
使用 managePgDatabase 的迁移能力执行，role 使用 postgres。
不要使用 PostgreSQL SQL 编辑器；不要 ALTER OWNER；不要重跑已完成迁移。
执行后返回：实际工具参数、RequestId、受影响对象和只读核验结果。
```

## 发布顺序

1. 在 CloudBase 测试环境执行 `schema.sql`（已有环境跳过）。
2. 执行 `concurrency-v2.sql`，但不要执行文件末尾注释的 `revoke update(...)`。
3. 通过 CloudBase AI 的 `managePgDatabase`、逻辑角色 `postgres` 执行 `concurrency-v3-special-roles.sql`。如果线上已经执行过 V3，不要重复执行，因为其中包含一次函数重命名。
4. 通过相同管理通道执行 `concurrency-v3-1-special-roles-hotfix.sql`。该文件使用 `create or replace`，可重复执行。
5. 执行 `verify.sql`，确认每一行 `ok` 都为 `true`。
6. 使用当前功能分支前端完成双浏览器验收。
7. 数据库验收通过后再发布新前端。
8. 确认线上新前端稳定后，执行：

```sql
revoke update(state, version, updated_at) on public.games from anon, authenticated;
```

9. 再次执行 `verify.sql` 并进行一次建房、加入、确认、描述、投票和下一轮回归。

> 已经完成 V3 的现有环境，本次只需以 CloudBase AI 管理通道的逻辑角色 `postgres` 执行第 4 步，不要重跑 V3。

## 双浏览器最小验收

- 两个独立匿名会话同时确认词语，两人的确认结果都保留。
- 两人同时提交描述，两条描述都保留。
- 两人同时投票，两票都保留；最后两票同时提交只结算一次。
- 同一按钮快速双击只生成一次提交。
- 首次平票只进入一次复投，旧票轮请求收到“状态已更新，请重试”。
- 两人同时爆灯只能一人成功。
- 描述公开后的 5 秒等待期内可以发起平民指认；指认后直接进入投票且清空旧票。
- 平民指认每局仅一次，进入下一轮后不能再次使用；“再来一局”后恢复一次机会。
- 等待房间修改三项人数配置后，其余玩法开关保持不变。
- 投票淘汰空白牌时按特殊阵营重新判胜；开启翻盘时，空白牌也进入私密猜词判定。
- 一个会话提交后断网并恢复，重新进入后能看到服务端已保存结果。

## 回滚

如果新前端发布后出现阻断问题：

1. 回滚前端到上一个稳定提交。
2. 若已经收紧权限，临时恢复旧前端写权限：

```sql
grant update(state, version, updated_at) on public.games to anon, authenticated;
```

3. `game_actions` 和 `apply_game_action` 可以保留，不影响旧前端读取房间。
