# 离谱法堂 V4 迁移操作说明

V4 基础迁移已由用户确认在 CloudBase 测试环境执行。后续只运行 V4.1 增量，不重跑、重命名或覆盖现有 V2、V3、V3.1 迁移和函数。

1. 先确认谁是卧底 V1.3.1 已通过 `verify.sql` 与双浏览器回归。
2. 在测试环境执行 `concurrency-v4-absurd-court.sql`，确认三张 `court_*` 表已启用 RLS，且 `anon` / `authenticated` 无直接表权限。
3. 同一窗口完整执行迁移中的 `apply_court_action`。它会在锁定 `games` 行后根据 `auth.uid()` 推导成员，拒绝客户端完整状态，并按 `actionId` 幂等处理。
4. 使用三个独立匿名浏览器会话验证三人同时提交辩护、补充和最后选票；核查 `games.state` 在公开前没有关键词、未公开正文、作者映射或个人票型。
5. 通过后才允许发布前端。不要在本迁移中执行生产部署、权限收紧或删除旧对象。

迁移会新增私密关键词、辩护和选票三张表；执行前请确认现有谁是卧底 V3.1 已稳定。若 SQL 编辑器提示函数 owner 不匹配，请按既有版本化 RPC 的方式新建函数，不要覆盖旧 `apply_game_action`。

## V4.1 可试玩增量

已经执行过 V4 时，不要重跑旧文件，直接执行 `concurrency-v4-1-court-playable.sql`。它会：

- 建立 20 条罪名、30 条突发证据和 60 条以上关键词的服务端内容池。
- 替换当前用户拥有的 `apply_court_action`，不修改谁是卧底的任何函数。
- 为同轮玩家无放回分配关键词。
- 在最后一人提交辩护、补充或选票后立即推进。
- 在结果阶段公开作者、本轮票数和最佳狡辩，并累计三轮得票。

执行后运行 `verify-v4-1-court-playable.sql`，确认所有 `ok` 都为 `true`。如果出现 `must be owner of function apply_court_action`，停止执行并提供函数 owner 查询结果，不要删除旧函数。

## Draft 0.2 / V5 增量迁移

Draft 0.2 已取消私密关键词、私密原因和私密证物。V5 不覆盖 V4/V4.1，而是新建版本化对象：

- `court_case_packs`：案件、证据和判词固定配套。
- `court_v5_submissions`：按房间、局次、轮次和玩家保存已确认的首次陈词与当庭补述。
- `court_v5_votes`：每名玩家每轮仅保存一张已确认选票。
- `court_v5_actions`：幂等键包含 `session_no`，防止“再来一局”与上一局冲突。
- `create_court_game_v5`、`join_court_game_v5`、`get_my_court_submission_v5`、`apply_court_action_v5`：V5 独立 RPC。

人工执行顺序：

1. 在 CloudBase 测试环境完整执行 `concurrency-v5-court-draft-02.sql`。
2. 执行 `verify-v5-court-draft-02.sql`，确认每一行 `ok` 均为 `true`。
3. 再部署包含 V5 前端的测试分支，避免前端先切换后因 RPC 尚未建立而无法建房。
4. 使用三个独立浏览器创建全新的 V5 房间。旧 V4 房间不会自动升级，也不用于 V5 验收。
5. 完成三轮并覆盖：同时确认、最后一人确认、超时未确认、暂离、匿名公开、每人一票、刷新恢复和房主“再来一局”。
6. 确认新局保留成员、清空比分与陈述，并且新局提交不会命中上一局记录。

V5 文件不包含 `drop`、`truncate` 或旧函数替换。如果 SQL 编辑器报 owner 错误，先停止并提供报错对象；不要删除或重命名 V4 函数。

## Draft 0.3 / V6 双项评选增量

V6 依赖已经核验通过的 V5，复用 `court_v5_submissions` 保存私密陈词，并新增：

- 案件包的 `reference_statement` 与 `reference_response`，只在投票阶段加入匿名候选。
- `court_v6_votes`：每名玩家每轮保存“最会狡辩”和“最像真的”两项选择。
- `court_v6_actions`：V6 独立幂等记录。
- `create_court_game_v6`、`join_court_game_v6`、`get_my_court_submission_v6`、`apply_court_action_v6`：V6 独立 RPC。
- 两人开局、两个独立奖项与两个玩家累计榜。

人工执行顺序：

1. 完整执行 `concurrency-v6-court-dual-vote.sql`。
2. 执行 `verify-v6-court-dual-vote.sql`，确认每一行 `ok` 均为 `true`。
3. 再部署包含 V6 前端的功能分支；旧 V5 房间不会自动升级。
4. 使用两个独立浏览器创建新房间，确认只有两人也能开始。
5. 验证参考答辩在首次陈词和补述阶段不可见，投票阶段以匿名编号出现，结果阶段才标记为“卷宗参考答辩”。
6. 验证两项可以选择同一候选、不能选择自己的陈述、确认后锁定、超时不会阻塞。
7. 完成三轮，确认本轮双奖项、狡辩排行榜、可信排行榜和再来一局均正确。

V6 不删除或覆盖 V5 对象。回滚前端时可保留 V6 表与函数，不要删除正在使用的 V6 房间数据。

## V1.6.1 内容增量

V6 的 11 项核验全部通过后，按以下顺序更新题库：

1. 执行 `content-v6-1-court-copy.sql`。它将启用题库更新到 30 套，停用偏严肃的旧“充电器缩水案”，并让“再来一局”保留最近 21 轮题目记录。
2. 执行 `verify-v6-1-court-copy.sql`，确认 6 行 `ok` 全部为 `true`。
3. 再部署包含 V1.6.1 的测试分支并创建新房间。已经开始的当前一局继续使用建局时选中的案件，不需要删除房间。
4. 连续点击“再来一局”完成至少 7 局，确认 21 轮题干不重复；第 8 局仍应优先选择不在最近 21 轮内的案件。

本增量不修改 V6 公共 RPC、投票表、计分或阶段时长。若替换 `court_v6_restart` 时提示 owner 不匹配，请停止执行并提供函数 owner，不要删除原函数。
